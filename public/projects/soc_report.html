01Project Overview & Motivation

An end-to-end SOC automation pipeline that replaces manual alert triage with AI-driven analysis — reducing response time from hours to seconds while maintaining analyst-grade accuracy.

Security Operations Centres face a fundamental scalability problem: alert volume grows exponentially while analyst capacity grows linearly. A typical SOC generates thousands of alerts per day, and analysts spend the majority of their time on repetitive Level-1 triage — classifying alerts, checking indicators against threat intelligence, and deciding whether an alert warrants investigation.

This project builds a fully automated triage pipeline where a self-hosted Large Language Model acts as a virtual Security Analyst. It receives enriched alerts, classifies them against the MITRE ATT&CK framework, scores severity, assesses false positive likelihood, and creates structured incident cases — all without human intervention for routine alerts.

🎯

Core objective: Build a SOC-as-a-Service platform that automates security alert triage using LLMs integrated with industry-standard open-source tools — proving that meaningful SOC automation is achievable with self-hosted AI and no proprietary vendor lock-in.

02System Architecture

A six-component pipeline where each tool handles a specific function — detection, orchestration, enrichment, analysis, classification, and case management — connected through internal APIs.

Detection

Wazuh SIEM

Monitors system logs (auth.log, syslog, file integrity events), runs detection rules, and fires alerts when meaningful security events are detected at configurable severity thresholds.

Orchestration

Shuffle SOAR

Receives alerts via webhook, extracts observables (IPs, hashes, domains), orchestrates enrichment through VirusTotal, routes enriched data to the AI engine, and dispatches results to case management.

Threat Intel

VirusTotal API

Provides IP reputation scores, file hash detections, malware family classifications, and abuse history for each observable extracted from the alert. Integrated directly into the SOAR workflow.

AI Analysis

Ollama + Mistral 7B

Self-hosted LLM running on dedicated infrastructure. Receives enriched alerts via a custom Flask microservice and returns structured JSON with severity scores, attack classification, MITRE mapping, and recommended actions.

Case Management

TheHive SIRP

Receives AI-enriched analysis and creates structured incident cases with MITRE tags, severity ratings, full AI analysis in Markdown, and all enrichment data attached for analyst review.

AI Microservice

Flask + Gunicorn

Custom Python service that acts as the bridge between the SOAR platform and the LLM. Constructs structured prompts, manages conversation context, and parses LLM output into actionable JSON.

End-to-End Pipeline Architecture
🛡️

Key design principle: Every component communicates exclusively through internal Docker networking. No service exposes endpoints to the public internet — alert flow stays entirely within the private infrastructure backbone.

03Alert Processing Pipeline

The complete journey of a security alert — from initial detection to enriched incident case — automated end-to-end with no manual intervention for routine events.

1. Log Monitoring & Detection

The Wazuh agent continuously monitors system logs — authentication events, syslog messages, and file integrity changes. Raw events are forwarded to the Wazuh Manager, which runs them against its rule engine. When a rule matches at a configurable severity threshold (e.g., level ≥ 5), the integration daemon fires an HTTP POST to the SOAR platform's webhook endpoint.

2. Observable Extraction & Enrichment

Shuffle receives the alert and immediately extracts three types of observables: source IP addresses, file hashes, and domain names. For each observable, it queries the VirusTotal API to retrieve reputation scores (how many AV engines flagged it), malware family classifications, and abuse history. The enrichment data is merged back into the original alert, creating a comprehensive enriched alert package.

3. AI-Driven Analysis

The enriched alert is forwarded to the custom Flask microservice, which extracts key fields (rule ID, severity level, description, source IP, user, log excerpt) and constructs a structured prompt. The prompt is sent to the self-hosted Ollama instance running Mistral 7B at temperature 0.1 for deterministic output. The LLM returns a structured JSON response containing: severity score (1–10), attack type classification, MITRE ATT&CK tactic and technique, analytical summary, recommended response action, and false positive likelihood assessment.

4. Case Creation & Triage

Shuffle takes the AI response and creates a fully enriched case in TheHive containing the alert title, a Markdown-formatted AI analysis description, MITRE ATT&CK tags, severity rating, and all enrichment data. The case is immediately available for analyst review — but for routine alerts, the entire pipeline completes without any human touchpoint.

04AI Analysis Engine

The core intelligence layer — a self-hosted Mistral 7B model with structured prompt engineering, deterministic output, and context-aware security analysis.

Why Self-Hosted AI?

Security alerts contain sensitive data — source IPs, usernames, file hashes, log excerpts. Sending this to a cloud API (OpenAI, Google, etc.) creates a data sovereignty risk. By self-hosting the LLM on dedicated infrastructure, all alert data stays within the controlled environment. No sensitive information leaves the network.

⚡

Performance trade-off: Self-hosted CPU inference is slower than cloud GPU APIs (~60s vs ~2s per analysis). This is an intentional architectural trade-off: data sovereignty and zero vendor lock-in take priority over raw speed. Async processing and hardware upgrades are planned mitigations.

Prompt Architecture

The AI microservice doesn't just forward raw alert text to the LLM — it constructs a carefully engineered prompt that frames the model as a Security Analyst with specific output requirements.

Prompt Construction — Structured Input

05Threat Intelligence Enrichment

Every alert is enriched with external threat intelligence before reaching the AI — ensuring the LLM makes decisions based on real-world reputation data, not just raw log content.

Observable Extraction & Enrichment Flow

The enrichment step is critical because it transforms the AI's analysis from pattern matching on log text into context-aware threat assessment. Without enrichment, a brute force alert from a residential IP and one from a known botnet C2 server would receive identical analysis. With enrichment, the AI can distinguish routine scanning from targeted attacks.

06Network & Infrastructure Design

A unified Docker backbone network where all services communicate through internal DNS — eliminating public IP dependencies and enabling secure, hostname-based service discovery.

Architecture Principles

Network

Single Backbone Design

All SOC services (SIEM, SOAR, AI service, case management, database) run on a single Docker bridge network with static IP assignments. This eliminates dual-homing complexity and ensures every service has one clear identity.

Discovery

Docker DNS Resolution

Services reach each other by container hostname (e.g., http://service-name:port) via Docker's built-in DNS. No hardcoded IPs, no external DNS dependencies, no service mesh overhead.

Security

Internal-Only Routing

The SIEM webhook fires internally to the SOAR container — never exposing the endpoint on a public IP. All inter-service traffic stays within the Docker network boundary.

Reliability

Health Checks & Auto-Restart

Every container has Docker health checks, restart policies (unless-stopped), and dependency ordering via depends_on. A systemd service ensures the entire stack survives host reboots.

Unified SOC Network Topology

Why This Design?

The original architecture had services split across multiple Docker networks with dual-homed containers, which created routing complexity and debugging challenges. The redesigned single-backbone approach simplifies everything: one network, one IP per service, hostname-based discovery via Docker DNS, and a clear path to adding network policies or mutual TLS for service-to-service authentication in the future — without requiring infrastructure redesign.

07Key Design Decisions

The engineering trade-offs and architectural choices that shaped this system — each with a clear rationale grounded in security operations requirements.

Decision 1: Self-Hosted LLM vs. Cloud API

✅ Self-hosted Ollama + Mistral 7B on dedicated infrastructure
❌ Cloud API (OpenAI GPT / Google Gemini)
Rationale: Security alerts contain sensitive organizational data (IPs, usernames, log excerpts, file hashes). Sending this to third-party APIs violates data sovereignty principles. Self-hosting ensures all data stays within the controlled infrastructure boundary, with zero vendor lock-in and no per-token costs.

Decision 2: Model Size — 7B vs. 3B Parameters

✅ Mistral 7B — superior MITRE mapping accuracy
❌ Llama 3.2 3B — marginally faster but degraded analysis
Rationale: The 3B model was benchmarked and rejected. Response times were only ~15% faster (~50s vs ~60s on CPU), but MITRE ATT&CK classification accuracy degraded significantly — the model frequently confused related tactics (e.g., Initial Access vs. Credential Access for brute-force events). Analysis quality is non-negotiable in a SOC context.

Decision 3: Dual-Server vs. Single-Server Architecture

✅ Two dedicated VMs — SOC stack + AI inference separated
❌ Everything on one server
Rationale: LLM inference is CPU-intensive and can starve other services of resources. Separating the AI engine onto dedicated hardware ensures that a 60-second inference cycle doesn't impact Wazuh detection, Shuffle orchestration, or TheHive case management. Each server can also be scaled independently.

Decision 4: LLM MITRE Mapping vs. Wazuh Static Tags

✅ Both — complementary layers of classification
❌ Rely solely on Wazuh's built-in MITRE tags
Rationale: Wazuh provides static, rule-based MITRE tags (a fixed tag per rule ID). The AI provides dynamic, context-aware classification — it can independently distinguish that a brute force event from a known botnet IP is Credential Access, while the same event pattern from an internal service account is more likely a misconfiguration. The two layers complement each other.

08MITRE ATT&CK Integration

How the AI maps every alert to the MITRE ATT&CK framework — providing standardized classification that enables cross-organization threat intelligence sharing and trend analysis.

MITRE ATT&CK Classification Pipeline
🔐

Dual-layer classification: The system deliberately maintains both Wazuh's static MITRE tags and the AI's dynamic classification. They serve different purposes — Wazuh provides fast, deterministic baseline tagging, while the AI adds contextual depth. When they disagree, it flags the alert for analyst review, creating a built-in quality assurance mechanism.
