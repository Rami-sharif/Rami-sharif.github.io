01Project Objective

Design and implement a secure, stable, and efficient communication infrastructure enabling centralized monitoring and control of 100+ ESP32-based IoT devices deployed across multiple geographic regions.

🎯

Core goals: Encrypted device-to-server communication via MQTT over TLS, scalable certificate management through a private PKI, VPN-only administrative access, and a layered security model that minimizes the attack surface at every tier.

02Network Architecture Design

A four-layer architecture separating edge devices, the security gateway, the core broker, and a DMZ for firmware updates — each with a distinct security boundary.

Edge Layer

ESP32 Devices

Distributed IoT devices sending telemetry and receiving commands. Connect to the broker over the public internet using MQTT secured with mutual TLS.

Security Gateway

pfSense Firewall

Cloud-hosted VPS acting as the public entry point. Handles firewall rules, NAT, OpenVPN tunnel management, and traffic filtering. The only component with a public IP.

Core Layer

EMQX MQTT Broker

Runs on an internal server reachable only through the VPN tunnel. Manages all publish/subscribe routing, device authentication, and message delivery.

DMZ

OTA & CA Server

Isolated zone hosting the firmware update server and the Step-CA certificate authority. Accessible only when needed, buffered from both external and internal networks.

System Architecture — Sanitized View
🛡️

Key design decision: The MQTT broker is never directly exposed to the internet. All device traffic enters through the pfSense gateway, which performs NAT and forwards it through an encrypted VPN tunnel to the internal server. This dramatically reduces the attack surface.

04MQTT Topic Design & Communication Flows

A structured topic hierarchy that cleanly separates telemetry, commands, command output, and device status — enabling scalable, organized device management.

Topic Hierarchy

iot/
  └── devices/
      └── {device_id}/
          ├── telemetry  ← periodic sensor readings (device → broker)
          ├── cmd         ← inbound commands (broker → device)
          ├── cmd/out    ← command execution results (device → broker)
          └── status     ← online/offline (retained message)

Flow 1: Telemetry — Device to Server

ESP32 reads sensors

Temperature, humidity, soil moisture, and light values are sampled on-device.

Publish to telemetry topic

Data is serialized as JSON and published to iot/devices/{id}/telemetry with QoS 1.

Broker routes to subscribers

The EMQX broker delivers the message to all subscribed dashboards and applications in real time.

Flow 2: Command — Server to Device

User sends command via HTTP API

A command (e.g., shell execution, interval change) is submitted through a dashboard or API endpoint.

Server bridges HTTP → MQTT

The server publishes the JSON command payload to iot/devices/{id}/cmd.

Device executes and responds

The ESP32 receives the command, executes it, and publishes the result (stdout, exit code, timestamp) to cmd/out.

💡

Centralized model: Devices never communicate directly with each other. All messages route through the broker, ensuring security, auditability, and message reliability.

05TLS vs mTLS — Authentication Model

Why mutual TLS was selected over standard TLS, and how it enforces device-level identity verification at the transport layer.

TLS vs Mutual TLS Handshake
FeatureTLSmTLS
Encryption✓✓
Server Authentication✓✓
Client Authentication✗✓
Security LevelMediumHigh
IoT SuitabilityLimitedIdeal
🔐

PKI architecture: A private Certificate Authority (Step-CA) runs in Docker. During provisioning, each ESP32 generates its private key on-chip, sends a Certificate Signing Request (CSR) to Step-CA, and receives a signed client certificate. The private key never leaves the device. At runtime, the EMQX broker verifies device certificates locally using the CA's root certificate — Step-CA is not contacted per connection.

06ESP32 Client Implementation

A Python-based MQTT client (MicroPython-compatible pattern) that handles TLS connection, telemetry publishing, command subscription, and bidirectional communication with the broker.

device_client.py — Core Connection Logic (Sanitized) 
# ── Broker connection settings ──
BROKER_HOST = "<GATEWAY_PUBLIC_IP>"
BROKER_PORT = 8883
DEVICE_ID   = "device001"

# ── Topic structure ──
TOPIC_TELEMETRY = f"iot/devices/{DEVICE_ID}/telemetry"
TOPIC_COMMANDS  = f"iot/devices/{DEVICE_ID}/cmd"
TOPIC_STATUS    = f"iot/devices/{DEVICE_ID}/status"
TOPIC_CMD_OUT   = f"iot/devices/{DEVICE_ID}/cmd/out"

# ── TLS setup ──
client.tls_set(ca_certs="ca.pem", tls_version=ssl.PROTOCOL_TLS_CLIENT)

# ── Last Will & Testament ──
# Broker auto-publishes offline status if device disconnects unexpectedly
client.will_set(TOPIC_STATUS,
    payload=json.dumps({"online": False, "ts": int(time.time())}),
    qos=1, retain=True)

# ── On connect: subscribe to commands, publish online status ──
def on_connect(client, userdata, flags, rc, props):
    client.subscribe(TOPIC_COMMANDS, qos=1)
    client.publish(TOPIC_STATUS,
        json.dumps({"online": True, "ts": int(time.time())}),
        qos=1, retain=True)

Client Capabilities

Telemetry

Periodic Sensor Publishing

Reads temperature, humidity, soil moisture, and light at configurable intervals (default 15s). Publishes JSON payloads with QoS 1 for guaranteed delivery.

Command Execution

Remote Shell Control

Receives JSON commands on the cmd topic, executes them asynchronously in background threads, and returns stdout/stderr/exit code on cmd/out.

Presence

Online/Offline Status

Uses MQTT retained messages and Last Will & Testament (LWT) to maintain accurate device presence — the broker automatically marks a device offline on unexpected disconnect.

Dynamic Config

Runtime Interval Adjustment

A special set_interval command changes the telemetry publish rate without requiring a restart or firmware update.

07Remote Shell Command Execution

The device simulator turns the MQTT broker into a full remote control channel — any shell command can be dispatched, executed, and its results returned in real time.

Command Payload Format

Accepted JSON Keys (all equivalent) 
// Any of these keys triggers shell execution:
{"cmd":     "whoami"}        // most common
{"exec":    "df -h"}         // alternative
{"shell":   "uptime"}        // alternative
{"command": "ip a"}          // alternative

// Special command — change telemetry interval:
{"set_interval": 5}         // publish every 5 seconds

Response Format

Published to cmd/out topic 
{
  "ok":      true,               // true if exit code = 0
  "rc":      0,                  // shell exit code
  "command": "whoami",           // exact command executed
  "output":  "root\n",           // stdout + stderr (last 8KB)
  "ts":      1711360000          // Unix timestamp
}
⚠️

Security note: Shell execution is deliberately powerful for authorized operators. In production, this capability is protected by mTLS (only devices with valid certificates receive commands), VPN-restricted broker access, and EMQX ACLs that limit which clients can publish to command topics.

08Server Hardening & Defence in Depth

A layered security approach where the MQTT broker server is protected at the network, firewall, transport, and access control levels — no single point of failure.

🌐

Network Isolation

The broker server has no public IP and is reachable only through the VPN tunnel. This eliminates direct internet exposure, preventing brute-force, port scanning, and protocol-level attacks.

🧱

Firewall Rules (UFW)

Default-deny incoming policy. Only VPN subnet traffic is allowed on specific ports: 8883 (MQTT/TLS), 22 (SSH), and the management dashboard. All other connections are silently dropped.

🔒

Transport Encryption (mTLS)

All device-to-broker communication uses mutual TLS on port 8883. The broker validates both the device certificate and its own server certificate, ensuring end-to-end encrypted and mutually authenticated channels.

🔑

SSH Hardening

Root login disabled. Access requires both an SSH key and a password (multi-factor). Only a single authorized admin user is permitted. VPN-only access further limits exposure.

UFW Firewall Rules — Structure 
# Default policy: deny all incoming, allow outgoing
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Allow MQTT over TLS from VPN subnet only
sudo ufw allow from <VPN_SUBNET> to any port 8883

# Allow SSH from VPN subnet only
sudo ufw allow from <VPN_SUBNET> to any port 22

# Allow EMQX dashboard from VPN subnet only
sudo ufw allow from <VPN_SUBNET> to any port 18083
SSH Hardening — sshd_config 
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication yes
AuthenticationMethods publickey,password    # Both required (MFA)
AllowUsers <admin_username>
