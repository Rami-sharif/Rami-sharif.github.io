01Project Overview & Motivation

A full-featured firewall simulation that captures, parses, inspects, and classifies network traffic in real time — providing hands-on understanding of how firewalls and intrusion detection systems work under the hood.

Traditional firewall education is abstract — students learn rules and policies in theory but rarely see the actual packet-level decision-making process. Commercial firewalls (pfSense, Cisco ASA) are black boxes that hide their internal logic behind proprietary interfaces and kernel-level hooks.

This project builds a transparent, fully observable firewall that runs in userspace. Every packet is captured by Scapy, parsed into structured fields, evaluated against a threat detector and configurable rule engine, and logged to a database — with every decision visible through a real-time web dashboard. The entire pipeline is designed to be inspectable, modifiable, and educational.

🎯

Core objective: Build a smart firewall and intrusion detection system that operates in simulation mode by default — capturing and analyzing real network traffic without actually blocking anything — allowing safe experimentation, learning, and demonstration without risk of disrupting network connectivity.

02System Architecture

A modular layered architecture where each component handles a single responsibility — capture, parse, detect, evaluate, enforce, and display — connected through clean internal interfaces.

Capture

Packet Sniffer

Uses Scapy to capture live IP packets from network interfaces in a dedicated background thread. Implements a stop filter mechanism and feeds raw packets into the processing pipeline.

Parse

Packet Parser

Extracts structured fields from raw packets: source/destination IPs, ports, protocol (TCP/UDP/ICMP), TCP flags, payload size, and raw payload data. Outputs a clean dictionary for downstream processing.

Detect

Threat Detector

Stateful detection engine using sliding window algorithms and in-memory deques. Detects SYN floods, port scans, ICMP floods, UDP floods, and rate-limit violations per source IP in real time.

Evaluate

Rule Engine

Evaluates each packet against user-defined firewall rules with priority ordering. Supports CIDR notation, port ranges, TCP flag matching, payload regex, time-based rules, and whitelist/blacklist overrides.

Enforce

Enforcer

In simulation mode, records BLOCK/ALLOW decisions to the database without touching iptables. When enforcement is explicitly enabled, applies real iptables rules with automatic cleanup on shutdown.

Dashboard

Flask Web UI

Real-time web dashboard with rule management, traffic logs, alert viewer, live traffic monitoring, and statistics charts. Built with Bootstrap 5 and Chart.js for interactive data visualization.

Layered System Architecture
🛡️

Key design principle: The engine layer (sniffer, parser, detector, rule engine) has zero dependencies on Flask. This means the entire packet processing pipeline can run independently — enabling unit testing with mock packets and headless operation without a web server.

03Packet Processing Pipeline

The complete journey of a network packet — from raw capture on the wire to a logged decision with full metadata — processed in milliseconds through a deterministic pipeline.

1. Packet Capture

The Sniffer runs Scapy's sniff() in a dedicated background thread, filtering for IP-layer packets. Each captured packet is immediately passed to the processing callback. The thread implements a stop_filter mechanism — though due to Scapy's blocking nature, the thread only terminates when the next packet arrives after a stop signal is issued.

2. Field Extraction

The Parser extracts structured fields from the raw Scapy packet object into a clean Python dictionary: source IP, destination IP, source port, destination port, protocol (TCP/UDP/ICMP), TCP flags (SYN, ACK, FIN, RST, PSH, URG), payload size in bytes, and the raw payload content. This normalized dictionary is the universal data format used by all downstream components.

3. Whitelist / Blacklist Check

Before any rule evaluation, the packet's source IP is checked against whitelist.txt and blacklist.txt. Whitelisted IPs bypass all detection and rules — they are always allowed. Blacklisted IPs are immediately blocked. This mirrors the behavior of production firewalls like pfSense and Cisco ASA, where trusted IPs skip the entire rule chain.

4. Threat Detection

The Detector runs its five algorithms against the packet, using in-memory sliding windows (deques) per source IP. If any detection threshold is breached — for example, more than 100 SYN packets in 10 seconds — the detector tags the packet with the threat type (e.g., syn_flood) and generates an alert entry. Detection state is held in memory for performance, not persisted to the database.

5. Rule Evaluation

The parsed packet is evaluated against all active firewall rules, sorted by priority (lower number = higher priority). The first matching rule determines the action (ALLOW or BLOCK). Rules support complex matching: CIDR notation for IP ranges, port ranges (e.g., 8000-8080), TCP flag combinations, payload regex patterns, and time-based windows that restrict rules to specific hours of the day.

6. Decision & Logging

The final ALLOW or BLOCK decision is written to the SQLite database along with full packet metadata: timestamp, IPs, ports, protocol, matched rule ID, detection tags, and the action taken. In simulation mode (default), no actual iptables rule is applied — the decision is logged and visible in the dashboard but has no effect on real traffic. When enforcement mode is explicitly enabled, the Enforcer applies real iptables DROP rules.

04Detection Engine (IDS)

Five specialized detection algorithms using stateful sliding window analysis — each tracking per-IP behavior patterns in memory to identify attack signatures in real time.

Detection Algorithms

Flood

SYN Flood Detection

Tracks TCP SYN packets per source IP using a time-windowed deque. Triggers when SYN count exceeds the threshold (default: 100) within the sliding window (default: 10s). Detects the most common denial-of-service attack vector.

Scan

Port Scan Detection

Monitors unique destination ports contacted per source IP. Triggers when distinct port count exceeds the threshold within the window. Identifies reconnaissance activity — attackers probing for open services before launching targeted attacks.

Flood

ICMP Flood Detection

Counts ICMP packets (ping) per source IP. Triggers on volume exceeding threshold in the window. Detects ping-of-death attacks and ICMP-based DoS — a simpler but still effective flooding vector.

Flood

UDP Flood Detection

Tracks UDP packet volume per source IP. Triggers when count exceeds threshold. UDP floods are commonly used in amplification attacks (DNS, NTP) where attackers use spoofed source IPs to overwhelm a target.

Sliding Window Detection — How It Works
⚡

Design trade-off: Detection state lives in memory (Python deques), not in the database. This means detection is extremely fast (no disk I/O during packet processing), but all state is lost on application restart. A long-running flood that spans a restart will not be detected. This is an intentional performance-over-persistence trade-off — the same approach used by Snort and Suricata for their stateful inspection engines.

05Rule Engine

A priority-ordered rule evaluation system with advanced matching capabilities — supporting everything from simple IP blocking to complex pattern-based filtering with time constraints.

Rule Evaluation Flow — First Match Wins
🧠

How _rule_matches works: The matching function checks each field sequentially — source IP (with CIDR support via Python's ipaddress module), destination IP, source port (with range parsing), destination port, protocol, and TCP flags. If all specified fields match, the rule matches. Unspecified fields are treated as wildcards. This is the same "match-all-specified-fields" logic used by iptables and every major firewall implementation.

06Simulation & Enforcement Modes

Two operational modes — simulation for safe learning and testing, enforcement for real packet blocking — with a built-in traffic simulator for generating controlled attack scenarios.

Operational Modes

Default

Simulation Mode

The firewall captures and analyzes real traffic, makes ALLOW/BLOCK decisions, logs everything to the database, and displays results in the dashboard — but never touches iptables. All decisions are recorded for review without any impact on real network connectivity. Safe for development, testing, and demonstrations.

Optional

Enforcement Mode

When ENFORCEMENT_ENABLED=True is set explicitly, the Enforcer applies real iptables -A INPUT -s <IP> -j DROP rules. Blocked IPs are tracked, and all iptables rules are automatically cleaned up on application shutdown via an atexit handler to prevent accidental lockouts.

07Key Design Decisions

The engineering trade-offs and architectural choices that shaped this system — each with a clear rationale grounded in educational value, safety, and practical software design.

Decision 1: Userspace vs. Kernel-Level Firewall

✅ Userspace with Scapy — observe and log, don't intercept
❌ Kernel module (Netfilter / nftables hook)
Rationale: A kernel-level firewall intercepts packets before they reach applications — but it requires C programming, kernel module compilation, and root access. A userspace approach using Scapy makes the entire pipeline inspectable with standard Python debugging tools, keeps the project portable across Linux distributions, and eliminates the risk of kernel panics or system-level lockouts during development.

Decision 2: In-Memory Detection State vs. Database Persistence

✅ Python deques in memory — zero-latency detection
❌ SQLite writes for every detection state update
Rationale: Flood detection runs on every single packet. Writing detection state to SQLite would introduce disk I/O on every packet — unacceptable latency at high packet rates. Deques provide O(1) append operations with automatic pruning of expired entries. The trade-off is state loss on restart, which is acceptable because detection is about real-time behavior, not historical patterns.

Decision 3: Simulation-First Default

✅ Simulation mode ON by default — safe out of the box
❌ Enforcement mode ON — block traffic immediately
Rationale: A firewall that blocks traffic by default on first run is dangerous — misconfigured rules could lock out SSH access, break DNS resolution, or isolate the host from the network. By defaulting to simulation, users can observe behavior, validate rules, and build confidence before opting into enforcement. This mirrors how production firewalls like pfSense handle rule deployment: test first, enforce second.

Decision 4: SQLite vs. PostgreSQL / External Database

✅ SQLite — zero-configuration, embedded, single-file
❌ PostgreSQL — requires separate installation and configuration
Rationale: The firewall is a single-user application — there is no concurrent multi-user access pattern. SQLite provides ACID compliance, supports the full ORM via SQLAlchemy, and requires zero setup — the database is a single file in the data/ directory. This makes deployment trivial: clone the repo, install dependencies, run. No database server to configure.
